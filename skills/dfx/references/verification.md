# 증거, 복구, 인계

## 완료 기준

실질적 편집 전에 성공을 확정하는 관찰 가능한 동작을 정합니다. 작은 요청에는 짧은 기준이면 됩니다. 큰 명세가 아닙니다.

- 버그: 가능하면 재현하고, 수정과 적절한 회귀 경로를 검증합니다.
- API: 바뀐 성공·실패 계약과 영향받는 소비자를 실행합니다.
- UI: 도구가 허용하면 렌더 결과와 관련 상호작용을 확인합니다.
- 리팩터: 기존 검사와 표적 보완으로 동작 보존을 검증합니다.

테스트 출력, 관찰된 동작, 검토한 코드를 증거로 씁니다. 통과한 테스트는 그것이 실행한 범위만 뒷받침합니다. 깨끗한 결과를 얻으려고 완료 기준을 낮추거나, 실패 테스트를 지우거나, 실행하지 않은 검사를 통과로 표시하지 않습니다. 기존 환경 문제로 인한 실패와 이번 변경이 만든 실패를 분리합니다. **완료를 선언하기 전에 검증 명령을 실제로 실행한 결과가 있어야 합니다.**

독립 판단이 가치 있는 변경에는 새 리뷰어(`dfx:reviewer`)를 씁니다. 사용자 의도, diff 또는 기준 리비전, 관련 파일, 테스트 명령과 결과를 주되 구현자의 결론으로 물들이지 않습니다. 리뷰어는 실제 diff 와 관련 코드를 봐야 합니다. 보안·성능·UX 리뷰는 조건부이며 필수 4표가 아닙니다. finding 에는 영향과 코드·재현 증거가 필요합니다. 추측성 스타일 선호는 자동 수정 대상이 아닙니다.

## 범위 한정된 복구

정당한 finding 을 고치고 영향받은 동작을 다시 확인합니다. 이후 변경이 무효화할 수 없을 때만 변하지 않은 통과 증거를 재사용합니다. 독립적으로 통과한 조각들이 상호작용하면 통합 결과를 검증합니다.

기본 정지 정책: 같은 문제에 대해 새 증거나 개선 없이 수리 2회를 시도했으면 원인과 범위를 재평가합니다. 실질적으로 다른 계획 1회 또는 더 강한 모델로의 인계 1회를 허용하고, 그래도 진전이 없으면 차단 요인을 기록하고 정직하게 인계합니다. 사용자의 예산·한도가 이 기본값보다 우선합니다. 진전이란 재현된 원인, 고쳐진 계약, 해결된 finding, 새로 통과한 관련 검사이지 메시지 수가 아닙니다. 끝없는 QC 루프를 시작하지 않습니다.

## Workflow 로 수렴 돌리기 (조건부)

다음 중 하나면 프롬프트로 루프를 굴리는 대신 `Workflow` 도구를 씁니다. `/dfx` 호출이 멀티에이전트 옵트인입니다.

- 독립 리뷰 렌즈가 3개 이상 병렬로 필요하고 각 finding 을 적대적으로 검증해야 할 때
- 발견→검증→수정→재검증 수렴이 2라운드 이상 예상될 때
- 변경 파일이 많아 검증 범위가 조정자 문맥을 넘길 때

작성 전 `workflow-authoring` 스킬을 로드합니다. 에이전트 출력은 `schema` 로 강제하고, 렌즈별 review 는 `pipeline()` 으로 흘려 한 렌즈의 검증이 다른 렌즈의 리뷰를 기다리지 않게 합니다. 수리 한도와 정지 정책은 위와 같습니다. 그 외 소규모 작업은 `Agent` 호출로 충분하며, 세션 기본 규모 지침(예: 15 에이전트 이하)을 따릅니다. `Workflow` 도구가 없거나 금지된 세션이면 렌즈별 리뷰를 한 메시지의 병렬 `Agent` 호출로 돌리고, 라운드 수는 위 정지 정책으로 묶습니다.

## 최소 지속 기록

위임·다단계 실행에는 대상 프로젝트의 `_workspace/dfx/<run-id>/` 아래 고유 디렉토리를 씁니다(UTC 타임스탬프 + 난수 접미사 또는 `mktemp -d`, 공유 `/tmp/dfx-current-run-id` 금지). 커밋에서 제외합니다. 추적되는 ignore 규칙을 기록용으로 고치지 말고 필요하면 `.git/info/exclude` 를 씁니다. 조정자만 공유 실행 상태를 씁니다. worker 는 필요하면 별도 증거 파일을 소유합니다. 자격 증명이나 원시 비밀 도구 출력을 저장하지 않습니다. 사소한 편집에는 이 기록을 만들지 않습니다.

`run.json` 하나를 유지하고, 명시적 재개 시 기존 실행을 씁니다.

```json
{
  "status": "running",
  "request": "사용자가 요청한 결과",
  "requirements": [{"id": "R1", "criterion": "관찰 가능한 동작", "evidence": []}],
  "tasks": [{
    "id": "T1", "goal": "한정된 결과", "depends_on": [],
    "write_scope": [], "status": "pending", "agent_id": null,
    "requested_model": null, "confirmed_model": null,
    "routing_reason": "", "repair_attempts": 0, "evidence": []
  }],
  "decisions": [],
  "blockers": [],
  "usage": {"input_tokens": null, "output_tokens": null, "source": null}
}
```

작업 상태: `pending`, `running`, `verified`, `blocked`. 실행 상태: `running`, `ready_for_review`, `blocked`, `cancelled`. 필수 작업과 검사가 충족됐을 때만 `ready_for_review` 로 둡니다. 남은 수동 확인은 제한 사항으로 적고, 필수인데 실행하지 못한 검사는 계속 blocking 으로 둡니다. 갱신한 JSON 은 형제 임시 파일에 쓴 뒤 원자적으로 교체합니다. 재개 시 현재 파일·diff 와 기록된 증거를 먼저 살핀 뒤 결과를 재사용합니다. 대화 문맥이 압축됐다는 이유만으로 완료된 작업을 다시 시작하지 않습니다.

`run.json` 은 복구 보조 자료이지 스케줄러·샌드박스·강제 토큰 예산이 아닙니다. 런타임이 노출하는 사용량만 출처·범위와 함께 기록하고, 겹치는 부모·자식 합계를 더하지 않습니다. 없으면 `null` 로 둡니다. Claude Code 의 Agent 완료 알림이 주는 subagent 토큰 합계는 작업별 `evidence` 에 출처(`agent-notification`)와 함께 적을 수 있지만, 모델 확인 메타데이터는 없으므로 `confirmed_model` 은 `null` 로 둡니다. 요청한 모델은 즉시 기록할 수 있지만 확인된 모델은 런타임 메타데이터에서만 적습니다.

인계 시 짧은 `report.md` 를 만듭니다. 요구사항별 결과와 증거, 실질적 변경, 실행하지 못한 검사·차단 요인, 모델 선택. 사용자 언어를 따릅니다. 사람의 최종 검토는 허가된 로컬 작업이 끝난 뒤이며, publish·merge·deploy 는 사용자의 실제 허가를 따릅니다.

dfx 저장소의 `scripts/qc_stuck_trends.py` 는 v1 감사 로그(`_workspace/<run-id>/04-qc/iter-N.json`) 전용이며 이 형식과 호환되지 않습니다.
