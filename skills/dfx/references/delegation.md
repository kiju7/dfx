# 위임과 작업 계약

## 호스트 어댑터 (Claude Code)

이 세션에 실제로 노출된 도구만 씁니다. `Task` 같은 옛 이름, 지어낸 역할, 위임을 흉내 내는 중첩 `claude -p` 는 쓰지 않습니다.

| 표면 | 위임 | 후속 |
|---|---|---|
| `Agent` | `subagent_type`, `prompt`, `description`, `model`, 선택 `isolation: "worktree"`(격리 트리) / `"remote"`(가용 시 클라우드) | 완료 알림, `SendMessage` 로 이어 쓰기, `ListAgents` 로 대상 확인 |
| `Workflow` | 스크립트가 `agent()`·`parallel()`·`pipeline()` 으로 팬아웃·수렴을 소유. 작성 전 `workflow-authoring` 로드 | 완료 알림, `/workflows` |
| 없음 | 가능하면 직접 수행하고 위임 불가를 밝힘 | — |

- **병렬 = 한 메시지에 Agent 호출 N개.** 나누면 순차입니다.
- 결과를 예측·창작하지 않습니다. 기다리는 동안 독립 작업을 하되 **위임한 탐색을 직접 반복하지 않습니다.**
- `SendMessage`·`ListAgents` 가 이름만 보이면 `ToolSearch`(`select:SendMessage`)로 먼저 불러옵니다.
- 에이전트 보고는 사용자에게 보이지 않습니다. 필요한 결과·증거는 조정자가 인계에 옮깁니다.

| `subagent_type` | 용도 |
|---|---|
| `dfx:worker` | build/explore 브리프 하나를 소유. 구현·검증·짧은 구조화 보고. 재위임 없음. 기본 `opus`, 호출별 `model` 로 덮어씀 |
| `dfx:reviewer` | 읽기 전용 독립 리뷰. 실행 증거가 있는 finding 만 반환. 기본 `opus` |
| `Explore` | 값싼 읽기 전용 위치 찾기 |
| `fork` | 대화 전체·부모 모델 상속, 도구 출력이 조정자 문맥에 쌓이지 않음. 대화 문맥이 필요한 넓은 읽기에. `model` 오버라이드 무시 |

개인 설치면 접두사 없이 `worker`/`reviewer`, 둘 다 없으면 `general-purpose` 에 같은 브리프를 주고 읽기 전용 제약은 프롬프트로 적습니다. 새 문맥에는 CLAUDE.md·권한 제약이 자동으로 따라가지 않을 수 있으니 적용되는 것을 브리프에 적습니다.

**교차 벤더 리뷰(조건부):** 목록에 `codex:codex-rescue` 가 있으면 영향 큰 변경의 최종 리뷰어 1명으로 씁니다. 없으면 생략하고 언급하지 않습니다.

**한도:** 동시 실행은 에이전트 수가 아니라 동시에 도는 빌드·테스트 부하로 잡습니다. 생성·재개가 한도 오류로 거부되면 노출된 상태부터 보고, 원인을 단정하지 않습니다. 상태가 바뀌었을 때 한 번만 재시도하고, 계속 거부되면 직접 수행하되 빠진 독립 리뷰를 밝힙니다.

## 분할

직무명이 아니라 **결합된 동작과 코드 의존성**으로 나눕니다. 병렬 소비자보다 공유 API·스키마 계약을 먼저 확정합니다.

**같은 작업 트리에 동시 쓰기 금지.** 공유 git index, 빌드 산출물(`target/`, `dist/`, `node_modules/`), 미완성 코드의 교차 컴파일 오류, 공유 설정(`package.json` 등) 때문에 파일이 달라도 깨집니다(실제 사고: 핸들러 6개 동시 작업 → lost-update·교차 테스트 실패). 병렬 쓰기는 둘 중 하나로만:

- 각 worker 를 `isolation: "worktree"` 로 격리하고 조정자가 순서대로 통합
- 파일 소유를 나누고 **빌드·테스트는 한 번에 하나**. worker 는 자기 파일 한정 검사만, 공유 스위트·전체 빌드는 조정자가 통합 후 1회

읽기 전용 리뷰에는 worktree 를 만들지 않습니다. 비슷한 N개 작업은 첫 번째를 기준 구현으로 삼아 후속 브리프에 패턴을 넘깁니다.

## 브리프

도움 되는 필드만 넣습니다.

```text
Goal: 사용자에게 보이는 결과 또는 구체적 질문
Context: 관련 요구사항·결정, 파일/심볼 포인터, 형제 작업 결과
Write scope: 허용 파일/모듈, 보존할 기존 사용자 변경
Done when: 관찰 가능한 완료 기준과 검사 명령
Constraints: 변경 원칙(요청 범위만·최소 코드), 적용 지침·권한, 동시 빌드 금지 여부
```

담당자는 코드를 읽고 구현을 다듬을 수 있지만, 목표·계약·소유권을 바꿔야 하면 증거와 함께 보고합니다. 도메인 주의점은 [domains.md](domains.md) 에서 해당 절만 붙입니다.

역할은 작업 모드입니다: **Explore**(읽기 전용 질문 답변), **Build**(동작 하나를 검증까지), **Review**(독립 검사, 편집 없음), **Integrate**(조정자가 합치고 공유 동작 검증).
