# Working on dfx

This repository has separate Claude and Codex entrypoints that share one design:
a short router skill plus references for routing, delegation, verification and
domain notes. Claude sources live in `skills/dfx`, `agents`, `.claude-plugin`;
Codex sources live in `codex/skills/dfx`. Read the relevant entrypoint before
changing behavior. Do not translate tool names or model aliases literally between
hosts (Claude: `Agent`/`Workflow`, `haiku/sonnet/opus/fable`; Codex: `spawn_agent`,
`luna/terra/sol/astra` with `reasoning_effort`).

Both skills use the host's native subagent tools, not a nested CLI runtime. Keep
entrypoints short; runtime-specific details belong in the linked references. No
mandatory agent count or fixed review pipeline for small tasks. When you change a
shared principle (work shapes, brief contract, stopping policy, run record), apply
it to both entrypoints in the same change.

Validate Python helpers with `python3 -m unittest discover -s scripts -p 'test_*.py'`.
Behavioral evaluations belong in disposable directories, never the user's
application repository. Run independent subagent evaluations when making
substantial orchestration changes; provide realistic tasks rather than expected
answers. Preserve evidence and report limitations rather than claiming benchmark
improvements from smoke tests. `scripts/qc_stuck_trends.py` reads v1 audit logs
(`_workspace/<run>/04-qc/iter-N.json`) and does not apply to v2 `run.json` records.

Judge policy changes by comparing representative tasks (small edit, feature,
coupled change, unclear defect, high-impact change) against a single-agent
baseline on the same revision; API dollar estimates and subscription quota are
not interchangeable.

The installer must preserve unrelated user skills and configuration. Do not
commit run artifacts, credentials, or generated bytecode.
